# v0.3.7 Cleanup Ledger — Runtime réteg auditja

> Állapot: 2026-08-01 · Vizsgált fájlok: 8 (teljes `Runtime/` mappa)
> Szabályok, amelyekhez mérünk: `DEVELOPMENT_HANDOVER.md` (3 réteg, Builder irány, Freeze, Experimental izoláció)

## Összefoglaló

A Runtime réteg **alapvetően egészséges**: a pipeline (GoTo → Analyze → Build → Play → Finished → Commit) a spec szerint működik, a `TransitionPlayer` tiszta (Evaluate + Finished, nem épít, nem tud a StateMachine-ről), a Startup Flash workaround pontosan a dokumentált `HideRoot → Capture → ShowRoot` formában van jelen, és a `VisualTreeUtility` használata is tetten érhető (`StateCapture`).

**Két építészeti szennyezés van**, mindkettő az Overlay kutatásból szivárgott a Stable kódba:

---

## F1 — 🔴 MAGAS: FigmaStateMachine hivatkozik az Experimental Overlay-re

**Fájl:** `FigmaStateMachine.cs` (`SelectPlayer`, `SubscribePlayer`, `UnsubscribePlayer`)
**Probléma:** A Stable StateMachine `GetComponent<OverlayTransitionPlayer>()`-t kér — ez az Experimental mappában élő kutatási kódra hivatkozik. Ez sérti:
- "A StateMachine NEM lehet Overlay Engine"
- "Semmi Experimental nem lehet referenciában a Stable Runtime felől" (`Experimental/README.md`)

Ha a v0.4-es asmdef szeparáció létrejön, **ez a fájl nem fog fordulni** — az Experimental asmdef nem elérhető a Runtime-ból.

**✅ VÉGREHAJTVA (2026-08-01, jóváhagyva):**
- Az Overlay ág kivezetve a StateMachine-ből (`SelectPlayer`, `SubscribePlayer`, `UnsubscribePlayer`)
- `AnimationMode.Overlay` → figyelmeztető log + Layout player fallback (a demók nem törnek, a viselkedés változatlan)
- Nem használt `using System.Diagnostics;` eltávolítva
- **Diff:** `docs/changes/F1_overlay_removal_from_state_machine.diff`
- A player-agnostic StateMachine (Finished esemény az ITransitionPlayer-re) a v0.4 feladata

## F4 — 🟠 KÖZEPES: Robusztusság (élesítési védelem)

**Fájl:** `FigmaStateMachine.cs`
**Probléma:** Nincs védelem: üres `states[]` (induláskor IndexOutOfRange), `profile == null` (Awake-ben NRE), `GoToState()` a capture befejezése előtt (NRE a `capturedStates`-en), `Build()` null eredménye (a player csendben visszatér, a `pendingState` fennakad).

**✅ VÉGREHAJTVA (2026-08-01, jóváhagyva):**
- `Awake`: `profile == null` → warning + Layout fallback (a SelectPlayer nem fut NRE-vel)
- `Start`: üres `states[]` → warning + `ShowRoot()` + megállás (a root NEM marad elrejtve!)
- `GoToState`: `capturedStates == null` (capture még fut) → warning + return
- `PlayTransition`: `transitionAsset == null` → warning + `pendingState` reset; üres transition (0 track) → **közvetlen commit** + `pendingState` reset (a Finished nem jönne, a gép nem akadna fenn)
- A tolerancia paraméterek `profile == null` esetén alapértékeket kapnak (F21)

## Tracks réteg auditja (2026-08-01 — 3 fájl, mind freeze 🔒)

### F13 — ✅ LEZÁRVA: PositionTrack flex vs absolute — a kettős mód tervezetten működik

- **Két mód:** (1) `useStyle` — ha a `resolvedStyle.left/top` eltér a két állapot között → `style.left/top` animálása; (2) egyébként `worldRect` delta → `style.translate` animálása
- Flex elrendezésnél a `left/top` 0/0, a `styleChanged` hamis → translate mód, ami a világkoordináta-deltát alkalmazza — **ez a helyes ág** flex esetén
- A translate mód a live fára mint "from" állapotra épül: a delta (`endRect - startRect`) a helyes eltolás, mert az animáció alatt a fa még a from állapotban van; a Commit új fát tölt be
- **Freeze:** nem módosítandó, a demók bizonyítják a működést. Limitáció (dokumentálva): ha a szülő elrendezése állapotonként változik és az elem nem absolute, a translate delta nem feltétlenül pontos — a v0.5 (Timeline/Shared Element) témája
